# Nexus-Ark-Discord-Custom（Nexus Ark v0.4.0.1 ベース）

**本家はケノ氏作成の [Nexus Ark](https://github.com/kenomendako/Nexus-Ark) です。**

複数のAIペルソナをDiscordで運用しやすくするための改造版です。v0.2.9版へ移植した独自機能について、Nexus Ark **v0.4.0.1** で構造が大きく変わったことを受け、再設計・移植を行っています。画像生成、Twitter承認、外部連携設定、UI、RAGなどを改善しています。

> おそらく永遠にベータ版。

相変わらずのデッドコピーです…。

## 改造に至った動機

旧改造の [Nexus Ark Multi Discord Custom 0.2.6版](https://github.com/Xen-Shuto/Nexus-Ark-Discord-Custom_0.2.6_old) で取り組んでいた内容をケノ氏へ共有したところ、本家でも元々実装を予定されていた機能とやりたいことの方向性がほぼ同じということで、ありがたいことに大部分を本家で実装していただいたのだが、そこはそれ、細かいところが気になったので独自にブラッシュアップすることにしたのである。

本改造では、本家で実装された機能を活用しながら、複数ペルソナのDiscord運用やTwitter投稿の確認、ローカル画像生成など、使い勝手をさらに調整したい部分を独自にブラッシュアップしています。

独自機能は一度v0.2.9版へ移植しました。その後、v0.4.0.1で本家の構造が大きく変わったため、新しい構成に合わせて再設計・移植を行い、重複する処理や設定の誤上書き、操作不能になるUI、ツール実行の不整合も整理しました。

## 1. 本家アップデート機能の停止

改造版へ本家の更新を適用し、ファイル構成や独自機能が崩れることを防ぐため、複数の入口で更新処理を停止しました。

- UIの更新確認・適用ボタンを無効化し、改造版では停止している旨を表示します。
- 更新ボタンの実行イベントを解除しました。
- 更新マネージャーの呼び出し口は残しつつ、更新確認・ダウンロード・適用を行わず、停止中のメッセージを返すようにしました。
- UIハンドラーを直接呼び出しても、更新は実行しません。
- ルートと`app`内の`update.js`から、Pinokio経由の`git pull`・依存更新などの処理を除き、停止通知だけを返します。
- Windows／シェルの起動処理から、終了コード123による再起動時のステージング更新適用を除きました。手動再起動の機能は維持しています。

主な対象：`Start.bat`、`app/Start.bat`、`app/start.sh`、`update.js`、`app/update.js`、`app/update_manager.py`、`app/nexus_ark.py`、`app/ui_handlers/__init__.py`。

## 2. ローカル画像生成と画像ファイル管理

### SD WebUI互換APIへの接続

- 画像生成プロバイダに`Local (SD WebUI)`を追加しました。
- SD WebUIを`--api`付きで起動し、`txt2img` APIへ接続して画像を生成できます。生成にはWebUIで選択中のモデルを使用します。
- API URL、サンプラー、Steps、CFG、固定ポジティブプロンプトの前置・後置、固定ネガティブプロンプトを保存できます。
- 手動生成画面でも正方形・縦長・横長、サンプラー、Steps、CFGを指定できます。
- ローカル生成時は外部画像生成APIキーを要求しません。参照画像は送らず、外部APIによる参照画像のキャプション生成も行いません。現状はテキストからの生成です。
- 接続タイムアウトは10秒とし、接続後の生成結果待ちには読み取りタイムアウトを設けず、生成完了を待つようにしました。

### 保存場所とファイル名

- 生成画像を保存先サブフォルダの`YYYY-MM`ディレクトリへ保存するようにしました。既定では`characters/<ルーム>/generated_images/YYYY-MM/`です。
- 手動生成・アイテム生成など、呼び出し側が指定する保存先にも同じ月別ルールを適用します。
- ファイル名を`プロバイダ名_ルーム名_時刻_UUID.png`の形式にし、同じ秒に生成しても上書きが起きにくい構成へ統一しました。ファイルは排他的に新規作成します。
- Gemini、OpenAI系、OpenRouter、Pollinations、Hugging Face、ローカル生成で保存名の生成処理を共有します。
- 過去画像の検索では、旧来の直下保存と月別ディレクトリの両方を探し、手動生成・アイテム生成の保存場所も対象にしました。

主な対象：`app/local_image_backend.py`、`app/generated_image_storage.py`、`app/tools/image_tools.py`、`app/nexus_ark.py`、`app/ui_handlers/__init__.py`。

## 3. ルーム切替時の外部連携設定の保護

- Twitter・Discordの設定を、ルーム切替時に対象ルームから読み直します。
- ブラウザ上の設定値と、その値を読み込んだルーム名を一緒に管理します。
- 設定の読み込み元と現在のルームが一致しない場合、切替中の場合、ルームが未選択の場合は保存を中止します。
- Discord Botの停止操作にも同じ確認を適用します。
- LINE設定は従来どおり全ルーム共通のまま、表示中のルームを基に保存・停止のタイミングを確認し、切替中の誤操作を防ぎます。
- LINE設定の読み込みボタンを追加しました。
- Twitterの保存結果は実際の処理結果を表示し、保存を中止した場合に成功メッセージで上書きしないようにしました。
- Twitter設定の読み込み・保存ボタンを、プライバシーフィルタなどの設定グループより下へ移しました。

ルーム切替時には未保存の編集が破棄されます。この動作を各設定画面に明記しています。

主な対象：`app/external_settings_guard.py`、`app/ui_handlers/twitter.py`、`app/ui_handlers/discord_line.py`、`app/nexus_ark.py`。

## 4. Twitter下書き・承認・画像添付

### 引用・リプライの承認必須設定

- `引用・リプライは承認必須`を追加しました。設定がない場合も有効として扱います。
- 有効時は自動投稿がONでも、返信先URL／IDの指定がある下書きや、本文にX／Twitterの投稿URLを含む引用投稿を承認待ちにします。
- 通常の単独投稿については、従来の自動投稿設定を使用します。

### Discordの承認ボタン

- 承認待ち下書きが作成されると、対象ルームのDiscord Botから既定チャンネルへ承認依頼を送ります。
- `承認して投稿`・`否認`・`詳細表示`のボタンを追加しました。既存の`/tw drafts`による一覧にも操作ボタンを付けます。
- 操作時にユーザー権限、チャンネル、下書きの所属ルーム、下書きの存在を確認します。
- Bot再起動後も、承認待ち下書きのボタン操作を登録し直します。
- 詳細表示ボタンは、承認待ちの間は何度でも使用できます。本文・返信先・警告・添付画像を、押した本人にだけ表示します。
- 詳細表示先へ承認ボタンを再出力しないため、詳細の連鎖やボタンの増殖を防ぎます。
- 画像が見つからない、またはDiscordへの添付に失敗した場合は、本文と警告を表示します。
- 承認して投稿に成功すると、操作した元の通知からボタンを削除し、`（承認されました。）`に置き換えます。否認完了時は`（否認されました。）`に置き換えます。
- 投稿失敗時は下書きへ戻し、ボタンを残して再試行できるようにしています。
- 同じ下書きの処理中の多重操作を抑止し、投稿処理にも下書きID単位の多重実行防止を加えました。

### 通知設定の意味を明確化

- `承認依頼を通知`は、Pushover／Discord Webhook経由の承認依頼通知にだけ適用される旨を追記しました。
- Discord Botによる承認ボタン送信は独立した処理です。Botの有効化・稼働、既定チャンネル、送信権限の条件を満たせば、このチェックがOFFでも送信します。
- 通知サービス側の通知禁止時間帯による抑制は、既存の動作を維持しています。

### 画像付き下書きと結果表示

- 画像付き投稿を要求されたのに`media_paths`が省略された場合は、下書きを作成する前にエラーとして返します。
- 指定された画像ファイルが存在しない場合も、保存前に拒否します。
- 会話中の画像タグから実在する候補パスを示し、モデルに`media_paths`の指定を促します。フォルダを走査して画像を自動選択する処理は追加していません。
- 能力要求の`intent`や`details`へ画像の説明を書くだけでは、画像添付にならないことをモデルへ明示します。
- 下書き作成の成功と通知送信の失敗を区別し、通知失敗だけを理由に「下書き作成失敗」と表示しないようにしました。UIには下書きIDと画像枚数も表示します。

主な対象：`app/twitter_manager.py`、`app/tools/twitter_tools.py`、`app/discord_manager.py`、`app/ui_handlers/twitter.py`、`app/agent/tool_execution_policy.py`、`app/agent/graph.py`、`app/utils.py`。

## 5. Discord会話・チャンネル情報・メディア送信

### 受信と応答の扱い

- 既定チャンネルIDを許可チャンネルとして扱い、許可リストへ重複登録しなくても受信・操作・送信できるようにしました。
- 許可ユーザー・チャンネル条件でメッセージを無視した場合に、理由をログへ残します。
- 自分へのメンション、ペルソナ名での呼びかけ、自分の発言への返信、別Bot宛てのメンションなどを区別する判定を追加しました。
- メンションや自分宛ての返信には返信形式、それ以外の通常応答にはチャンネルへの通常投稿を使用します。モデルの`<action:reply/>`指定でも返信形式にできます。
- 許可ユーザーがBot自身の発言へ付けたリアクションを会話入力として扱えるようにしました。
- 応答全体が`[SILENCE]`だけの場合に発言を抑制し、通常の文章中でその語を説明している場合まで無言にしないようにしました。

### ペルソナによる情報取得

- `list_discord_channels`を追加し、このペルソナが設定上許可され、かつBotに閲覧・送信権限があるチャンネルを取得できます。
- `list_discord_channel_members`を追加し、許可されたチャンネルのメンバー情報を取得できます。
- 取得対象は「チャンネルを閲覧できるメンバー」であり、現在画面を見ている人やオンラインユーザーを示すものではありません。
- 完全取得には`チャンネルのメンバー一覧を完全取得する`設定と、Discord Developer Portal側の`SERVER MEMBERS INTENT`が必要です。不完全な場合は部分一覧であることを返します。

### 画像・動画ファイルの検出を共通化

- 通常返信、グループ会話、自律送信で同じメディア検出処理を使用します。
- 専用画像タグ、Markdown画像、引用符で囲まれたパス、本文中のファイルパス、明示的な添付指定を統合します。
- 実在するローカルファイルのみを添付し、パスの重複を除きます。リモートURLを自動ダウンロードする処理はありません。
- 画像に加え、検出対象にはMP4／WebMも含まれます。

### 停止・再起動処理

- 接続終了処理を待ってからイベントループを閉じるようにしました。
- 残っているタスク、非同期ジェネレーター、実行スレッドの後始末を行います。
- 旧Botの停止が完了する前の再起動や、古いセッションの終了処理が新しいセッション登録を消すことを防ぎます。

主な対象：`app/discord_manager.py`、`app/discord_message_policy.py`、`app/tools/discord_tools.py`、`app/config_manager.py`、`app/agent/tool_registry.py`、`app/agent/graph.py`。

## 6. 能力要求・差し戻し・画像生成回数の制御

- `request_capability`は実ツールを提示するための受付であり、作成・承認・投稿の成功を意味しないことを明記しました。
- 未対応カテゴリや、Twitter連携が無効なルームでのTwitter能力要求は受け付けず、未実行であることを返します。
- 無効なTwitterツールをモデルへ提示しないようにし、ツール登録のフォールバック経路と実行直前にも同じ制限を適用します。
- 差し戻しの保留状態を、要求したカテゴリの実ツールと対応付けました。無関係なツールの実行だけでは、要求が済んだ扱いにしません。
- 該当ツールを試行した場合は、失敗していても「まだ一度も実行していない要求」として再度促さないようにしました。
- 差し戻し回数を会話ターン内で管理し、最大1回に制限します。終了指示、ツール無効、ループ上限などの条件も確認します。
- 差し戻し指示に、ユーザーの指定回数・枚数を増やさず、成功済みの処理を重複実行しない旨を追加しました。
- 「画像を2枚」のような明確な日本語の指定がある場合、ターン内の画像生成試行回数を制限します。同じ応答で複数回要求された場合も、上限を超えた呼び出しは実行しません。
- 失敗やタイムアウトでも、生成サーバー側では処理が進んでいる可能性があるため、試行回数として数えます。
- 「各2枚」「2枚ずつ」「2枚以上」などの曖昧・分配的な指定や、枚数未指定、自律行動には、この単純な枚数制限を適用しません。

主な対象：`app/agent/graph.py`、`app/agent/tool_execution_policy.py`、`app/agent/tool_registry.py`、`app/tools/capability_tools.py`、`app/gemini_api.py`。

## 7. UIの操作不能・表示更新への対策

- Gradio 6.14.0の既知のタブ部品に対し、内容が変わっていない子タブ情報の再登録を抑止し、更新ループを防ぐ互換処理を追加しました。
- 表部品では、過去の設定参照が積み重なる処理や、不要なページ状態のリセット、更新通知の循環を抑止しました。
- 表のデータ・列・表示状態の変更を追跡し、更新時に再描画を通知します。Twitterの「承認待ちを更新」で、別タブへ移動しなくても一覧が反映されるようにしました。
- 修正済み表部品には別の配信名を使い、古い配信ファイルが再利用されにくい構成にしています。
- 互換処理は対象のGradioバージョンと配信ファイルのハッシュを照合して適用します。インストール済みライブラリのファイルを直接書き換えません。
- 右上の「…」メニューが本文や子タブの背面に回り、クリックできなくなる問題に対して、タブヘッダーの重なり順を修正しました。
- 外部連携設定のためだけの追加`demo.load`登録を避け、初期表示値とルーム切替イベントで設定を反映します。
- 自己意識表示の内部状態ハンドラーについて、戻り値の型情報と空データの列名を実際の8出力・感情表示の構成に合わせました。

主な対象：`app/gradio_ui_compat.py`、`app/gradio_dataframe_compat.py`、`app/assets/styles/nexus_ark.css`、`app/nexus_ark.py`、`app/ui_handlers/__init__.py`。

## 8. RAG更新と不要処理の整理

### 索引更新の共通化と途中再開

- 記憶・知識・現行ログのバッチ索引作成を共通処理へ集約しました。
- 文書内容と識別用メタデータからチャンクIDを作り、既存索引に保存済みのチャンクを再作成しないようにしました。
- 埋め込み計算の完了後に索引へ追加し、バッチ単位で保存します。完了記録は保存成功後に進めます。
- メモリ不足や埋め込み処理の失敗で中断しても、保存済みチャンクを基準に、次回は未作成分から再開します。
- 古い完了記録を一度見直す印を導入し、旧処理で未完了なのに完了扱いになっていた場合を再走査できるようにしました。
- 知識索引では未変更チャンクを再利用し、不要になったチャンクを除きます。
- 現行ログは補助情報ファイルだけに依存せず、索引本体を確認して再開位置を判断します。
- 索引更新前に該当する読み取りキャッシュを外し、保存に失敗した未確定チャンクを保存済みと誤認しないようにしました。
- 同期版の記憶更新も進捗付き処理を利用し、同じ更新ロジックの重複を減らしました。

APIエラー時のキー切り替えなど、既存のAPI選択・再試行方針は継承しています。旧改造の独自APIキーローテーション方式を追加した変更ではありません。

### 履歴・モデル・重複定義の整理

- 同じローカル埋め込みモデルを複数の用途・RAG管理オブジェクトで共有できるようにしました。弱参照キャッシュと初期化ロックを使用します。
- 通常の履歴読み込みでは、絶対位置が不要な場合に未読の過去ログ全体の件数を数えないようにしました。絶対位置が必要なUI操作では従来どおり計算します。
- 履歴配列の先頭へ繰り返し挿入する処理を、末尾への追加と一度の反転へ変更しました。
- ログキャッシュのキーと無効化処理を正規化し、Windowsのパス区切りや大文字・小文字の違いでも同じファイルとして扱います。
- キャッシュヒット数を読み込みループで集計し、表示のために同じファイル情報を取り直す処理を減らしました。
- 研究ノートは本文全体を保持せず、最新10件の見出しを取得する共通処理へまとめました。
- コンテキスト作成とトークン計算で、同じルームファイルパスの重複取得を減らしました。
- 後続の定義やモジュール取り込みで上書きされる旧UIハンドラー、および到達しない`return`を削除しました。

主な対象：`app/rag_manager.py`、`app/utils.py`、`app/agent/graph.py`、`app/gemini_api.py`、`app/ui_handlers/__init__.py`、`app/room_manager.py`。

## 9. Web検索の設定・テスト・エラー報告

- 「検索テスト」をGoogle専用から、選択中の検索プロバイダを使用する処理へ変更しました。
- DuckDuckGoのテストではGeminiキーやGeminiモデルを使用せず、TavilyはTavily、Googleは選択されたGeminiモデルとキーでテストします。
- Google用の検索モデル指定とモデルリスト取得は、Google選択時だけ表示します。
- 検索プロバイダが「無効」の場合、検索テストボタンを無効にします。
- DuckDuckGo検索は専用エンジンを使用し、複数検索先の自動初期化による`primp`のブラウザ互換設定エラーを避けます。
- 検索結果をまとめる前のHTTP応答を確認し、明示的な0件、アクセス確認画面、HTTPエラー、取得・解析不能を区別して返します。
- 検索結果のリンク・本文を整形し、リダイレクト形式のリンクは元のURLへ展開します。結果は最大5件です。
- アクセス確認が要求された場合に自動で突破したり、別の検索サービスへ切り替えたりする処理はありません。DuckDuckGo側の制限により、検索できない場合はその状況を返します。

主な対象：`app/tools/web_tools.py`、`app/ui_handlers/__init__.py`、`app/nexus_ark.py`。
